### Алхам 2-ын өөрийн шалгалт

- **Итгэмжтэй:** Бодит хэрэглэгчийн үйлдэл болон бодит системийн эвдрэлийг өдөөлт болгон тодорхойлсон.
- **Үнэ цэнэтэй:** Хариу өгөх хугацаа, төлбөрийн алдаа, системийн зогсолт зэрэг хэрэглэгчид шууд нөлөөлөх үзүүлэлтүүдийг хэмжинэ.
- **Тодорхой:** VU, хүсэлт/секунд, туршилтын хугацаа болон эвдрэлийн хугацааг тодорхой заасан.
- **Нарийн:** Endpoint, өдөөлт, хүлээгдэж буй хариу болон хэмжүүр бүрийг тусад нь тодорхойлсон.
- **Ойлгомжтой:** Бүх сценарио ижил 6 хэсэгтэй бүтэцтэй бөгөөд хэмжүүрүүд нь тоон босготой.

## Сценарио бүрээс SLO гаргах

| Сценарио         | SLI (юуг хэмжих)            | Босго               | Цонх / нөхцөл                                        |
| ---------------- | --------------------------- | ------------------- | ---------------------------------------------------- |
| **Performance**  | `/cart/add` latency         | **p95 < 4 ms**      | **20 VU** тогтмол ачаалалд, **1 минут**              |
| **Reliability**  | `/pay` error rate           | **< 8%**            | **20 VU**, **1 минут**                               |
| **Availability** | Бүх хүсэлтийн амжилтын хувь | **p95 ≥ 90%**       | **20 VU**, **2 минут**, **10 секундийн crash** орсон |
| **Availability** | Сэргэх хугацаа              | **p95 ≤ 10 секунд** | **10 секундийн crash**-ийн дараах recovery           |

### SLO босго сонгосон шалтгаан

`/cart/add` endpoint-ийн **p95 < 4 ms** босгыг хэрэглэгчийн сагсанд бараа нэмэх үйлдэлд мэдэгдэхүйц саатал үүсгэхгүй байх зорилгоор сонгосон. `/pay` endpoint-ийн **8%-ийн error rate** босгыг туршилтын үед бага хэмжээний төлбөрийн алдаа гарах боломжийг тооцож, хэт хатуу бус боловч найдвартай ажиллагааг шалгах зорилгоор сонгосон. Availability-ийн **90%** босго нь 10 секундийн crash-ийг 2 минутын туршилтын цонхонд багтаан системийн recovery-г шалгах боломж олгоно.

### Availability Error Budget

Availability SLO:

**90%**

Туршилтын цонх:

**2 минут = 120 секунд**

Тиймээс зөвшөөрөгдөх downtime:

**120 × (1 − 0.90) = 12 секунд**

Иймээс availability-ийн **time-based error budget = 12 секунд** байна.

Энэ нь туршилтын 2 минутын цонхонд систем нийтдээ **12 секунд хүртэл** unavailable байхыг SLO зөвшөөрч байна гэсэн үг.

## Мини chaos

Серверийг туршилтын явцад **10 секундээр унтрааж**, availability-д үзүүлэх нөлөөг хэмжсэн.

Туршилтын нийт хугацаанд **5703 HTTP хүсэлт** илгээгдсэн. Сервер унтарсан үед хүсэлтүүд амжилтгүй болж, нийт `http_req_failed` **13.44%** болсон.

| Үзүүлэлт               |     Үр дүн |
| ---------------------- | ---------: |
| Нийт HTTP хүсэлт       |       5703 |
| HTTP failure rate      | **13.44%** |
| Checks                 | **86.55%** |
| Availability SLO       |  **> 90%** |
| Availability threshold |   **FAIL** |

Endpoint тус бүрийн үр дүн:

| Endpoint  | PASS | FAIL | Failure rate |
| --------- | ---: | ---: | -----------: |
| `/cart`   | 1681 |  220 |   **11.58%** |
| `/report` | 1677 |  224 |   **11.78%** |
| `/pay`    | 1578 |  323 |   **16.99%** |

Нийт `checks`-ийн хувьд:

```text
Checks succeeded = 4936 / 5703 = 86.55%
Checks failed    = 767 / 5703 = 13.44%
```

Серверийг 10 секундээр зогсоосны улмаас хүсэлтүүдийн тодорхой хэсэг амжилтгүй болсон. Үүний үр дүнд `http_req_failed` **13.44%** болж, `checks` **86.55%** хүртэл буурсан.

Availability-ийн шаардлага нь:

```text
checks > 90%
```

байхад хэмжилтийн үр дүн:

```text
checks = 86.55%
```

болсон тул **Availability threshold FAIL** болсон.

Мөн k6-ийн төгсгөлийн мэдээлэлд:

```text
thresholds on metrics 'checks, http_req_failed{name:pay}' have been crossed
```

гэж гарсан нь `checks` threshold болон `/pay` endpoint-ийн `http_req_failed` threshold хоёулаа зөрчигдсөнийг харуулж байна.

### Error budget хэтэрсэн эсэх

Энэ үр дүнгээс харахад 10 секундийн crash нь тухайн ачааллын үед олон хүсэлтэд зэрэг нөлөөлж, request-based availability-г 90%-аас доош оруулсан байна.

### Error budget

Availability SLO-г 90% гэж үзвэл 2 минутын туршилтын цонхонд зөвшөөрөгдөх downtime:

```text
120 × (1 − 0.90) = 12 секунд
```

Иймээс time-based error budget нь **12 секунд** байна.

Гэтэл:

```text
Actual downtime = 10 секунд
Error budget    = 12 секунд
```

өөрөөр хэлбэл 10 секундийн зогсолт нь дангаараа **12 секундын time-based error budget-ийг хэтрээгүй**.

Гэхдээ хүсэлтээр хэмжсэн availability нь:

```text
checks = 86.55%
```

болсон тул **90%-ийн SLO хангагдаагүй**.

Энэ ялгаа нь k6-ийн `checks` болон `http_req_failed` нь хугацаагаар бус **хүсэлтийн тоогоор** хэмжигддэгтэй холбоотой. Сервер хэвийн үед `/report` endpoint ойролцоогоор 200–400 ms зарцуулж байгаа бол сервер crash болсон үед хүсэлтүүд `connection refused` зэрэг алдаагаар хурдан буцаж болно.

Туршилтын нийт throughput:

```text
5703 requests / 121.4 seconds ≈ 47 requests/second
```

байсан. Тиймээс сервер унтарсан 10 секундын хугацаанд олон тооны хүсэлт зэрэг амжилтгүй болж, нийт request-based failure rate-д мэдэгдэхүйц нөлөөлсөн.

Иймээс **12 секундын time-based error budget** болон **13.44%-ийн request-based failure rate** нь хоорондоо шууд адил утгатай биш юм.

### Нэмэлт ажиглалт

`/pay` endpoint хамгийн өндөр failure rate-тай байсан:

```text
/pay = 323 / 1901 = 16.99%
```

Мөн k6-ийн threshold output-д:

```text
http_req_failed{name:pay}
```

threshold зөрчигдсөн гэж тодорхой гарсан. Иймээс chaos туршилтын үед `/pay` endpoint-ийн availability бусад endpoint-үүдээс илүү ихээр муудсан байна.

### Availability ба reliability тусгаарлах

Availability SLI-г "хүсэлт серверт хүрч хариу авсан эсэх" (connection error, timeout, status 0-ээр) гэж, reliability SLI-г "хариу авсан хүсэлтүүдийн дотор зөв хариу (2xx, зөв body) буцсан эсэх" гэж тодорхойлбол crash зөвхөн availability-д, харин 5xx буцаадаг bug зөвхөн reliability-д нөлөөлж, хоёр SLI өөр өөр эвдрэлийг хэмжинэ.

## Threshold зориуд эвдэх

`/report` endpoint-ийн `p(95)<100` threshold-ийг шалгахын тулд `slo-test-fail.ts` скриптийг тусад нь үүсгэж ажиллуулсан.

### Threshold

```js
thresholds: {
  'http_req_duration{name: cart}': ['p(95)<50'],
  'http_req_duration{name: report}': ['p(95)<100'],
  'http_req_failed{name:pay}': ['rate<0.08'],
  checks: ['rate>0.90'],
}
```

### Үр дүн

| Endpoint    |  Threshold | Бодит p(95) | Үр дүн |
| ----------- | ---------: | ----------: | ------ |
| `/cart/add` |  `< 50 ms` |      2.3 ms | PASS   |
| `/report`   | `< 100 ms` |   389.09 ms | FAIL   |

`/report` endpoint-ийн бодит `p(95)` нь `389.09 ms` байсан тул `p(95)<100` threshold-ийг хангаагүй.

FAIL болсон үед k6-ийн гаралтад threshold зөрчигдсөн тухай мөр гарна:

```text
✗ 'p(95)<100' threshold on http_req_duration{name: report} has been crossed
```

Linux/macOS дээр exit code-ийг дараах командаар шалгасан:

```bash
echo $?
```

Threshold FAIL болсон үед k6:

```text
99
```

гэсэн exit code буцаана.

`99` нь k6 тест ажилласан боловч нэг буюу түүнээс олон threshold зөрчигдсөнийг илэрхийлнэ. CI pipeline энэ non-zero exit code-ийг ашиглан build-ийг амжилтгүй болгох боломжтой.

### Яагаад `/cart/add` PASS хэвээр байгаа вэ?

`/cart/add` endpoint нь localhost дээр маш хурдан хариулдаг. Хэмжилтээр `p(95)=2.3 ms` байсан бөгөөд энэ нь `50 ms`-ээс бага байна.

Харин `/report` endpoint нь сервер талдаа ойролцоогоор 200–400 ms зарцуулдаг тул `p(95)<100 ms` шаардлагыг хангаж чадахгүй.

Иймээс ижил `p(95)` хэлбэрийн threshold ашигласан ч endpoint бүрийн бодит response time өөр учраас `/cart/add` PASS, `/report` FAIL болж байна.

## Дүгнэлт

Энэ ажлаар performance, reliability, availability гэсэн гурван чанарын шинж чанарыг сценарио болгон тодорхойлж, тэдгээрээс тоон SLO гаргаад k6-ээр хэмжсэн. Мини chaos туршилтад серверийг 10 секунд унтраахад 5703 хүсэлтийн 13.44% амжилтгүй болж, checks 86.55% хүртэл буурсан тул 90%-ийн availability threshold FAIL болсон. Endpoint тус бүрээс /pay хамгийн өндөр буюу 16.99%-ийн алдаатай байсан. 10 секундийн зогсолт нь 12 секундийн time-based error budget-д багтсан ч request-based хэмжилтээр SLO зөрчигдсөн. Учир нь сервер унасан үед хүсэлтүүд connection refused-ээр бараг шууд буцаж, нэг секундэд илүү олон алдаатай хүсэлт бүртгэгддэг. Иймээс time-based болон request-based error budget нь шууд адил утгатай биш бөгөөд SLI-г ямар аргаар хэмжихээ эхнээс нь сонгох хэрэгтэйг харуулсан. Нэг эвдрэл availability болон reliability хоёр SLO-г зэрэг зөрчиж болох тул хоёр SLI-г тусгаарлах нь чухал юм. Availability-г "хариу ирсэн эсэх", reliability-г "ирсэн хариу зөв эсэх" гэж хуваавал crash болон 5xx bug өөр өөр хэмжигдэнэ. Threshold зориуд эвдэх туршилтаар /report-ийн бодит p(95) нь 389.09ms байж 100 ms-ийн босгыг хангаагүй (FAIL), харин /cart/add нь 2.3 ms-ээр PASS болсон. Endpoint бүрийн бодит latency өөр тул threshold-ийг endpoint тус бүрт тусад нь тогтоох ёстой. Threshold зөрчигдөхөд k6 нь exit code 99 буцаадаг тул CI pipeline-д ашиглаж, SLO зөрчсөн build-ийг автоматаар зогсоох боломжтой.
